# Контракт ЛР4

Основа — итог ЛР3, commit `efe8ce6921ef0fd721497a1af3c922e1c0359d56`.
Этот документ задаёт договорённости для параллельной работы команды.
В текущем каркасе готовы схема, фикстуры, подключение и общий захват пары.
Бизнес-методы и новые HTTP-маршруты реализуются следующими PR.
`cmd/server` пока запускает прежнюю сборку ЛР3 с памятью.

## Разделение работы

| Автор | Методы `postgres.Store` | Файлы реализации | Обязательные проверки |
| --- | --- | --- | --- |
| Арина | `Like`, `PairMatched` | `internal/postgres/likes.go`, `pairs.go`; существующий `internal/likehttp` | Успех, повтор, взаимность, промежуточный откат, встречные Like через разные соединения |
| Даша | `Block`, `Profiles`, `LikedIDs`, `BlockedIDs` | `internal/postgres/blocks.go`, `discovery.go`; существующие application/discovery и discoveryhttp | Блокировка до/после Like, оба порядка конкуренции Like/Block, актуальная выдача |
| Полина | `ReadProfile`, `UpdateProfile` | `internal/postgres/profiles.go`, новый `internal/profilehttp` | Успех, чужой actor, отсутствие, старая версия, сохранность первой правки |
| Марго | `Unlike`, общая основа и подключение | `internal/postgres/unlike.go`, общий `store.go`/`transaction.go`, сборка сервера | Отзыв, повтор, откат, оба порядка Unlike/Like, общий HTTP-сценарий и перезапуск |

Интерфейсы и точные сигнатуры находятся в `internal/application/lr4_contract.go`.
Результаты команд — в `internal/domain/lr4.go`; существующие `PairKey`,
`PairState` и `LikeDecision` сохраняются.
Каждая операция принимает request context. Для Like application сначала
вызывает прежнюю проверку профилей через Profile API, затем `Store.Like`.
Отказы Profile API сохраняют коды ЛР3. Другие операции внешнюю сеть не вызывают.

В начале каждая может писать обработчики и application-код с небольшой
fake-реализацией своего интерфейса. Итоговые проверки транзакций выполняются
с реальными `Store` и PostgreSQL. Каждая авторка добавляет свои тесты вместе
с операцией, в том числе проверки отката после выполненного SQL.

## Данные

| Таблица | Поля | Назначение и ограничения |
| --- | --- | --- |
| `profiles` | `id`, `name`, `bio`, `photo_url`, `active`, `movies`, `music`, `books`, `position`, `version` | Профили и фиксированный порядок выдачи. PK по ID; уникальная положительная position; version > 0; обязательные поля |
| `pairs` | `left_id`, `right_id`, `left_liked`, `right_liked`, `left_blocked`, `right_blocked` | Одна каноническая пара. PK по двум ID; FK на профили; CHECK left_id < right_id |
| `matches` | `left_id`, `right_id`, `active` | Не более одной записи мэтча на пару. Составной PK и FK на `pairs` |

Сравнение ID в БД использует collation `C`, соответствующий порядку строк
в `domain.NewPairKey`. `left_liked` — Like от left к right; `left_blocked` —
блокировка от left к right. Аналогично для right. Нельзя хранить второй набор
тех же реакций или блокировок в памяти рабочего сервера.

`name` содержит от 1 до 100 символов после удаления пробелов по краям,
`bio` — до 2000 символов. В миграции также есть `photo_url text NOT NULL`;
его значение пока не редактируется. Поля `active`, интересы, фото и position
задаются фикстурами и в этой работе не изменяются.

Profile API сохраняется как внешняя проверка наличия/активности до транзакции.
Его изменяемые внешние факты не входят в гарантию PostgreSQL. Режимы missing,
error, slow и large продолжают демонстрировать отказы зависимости, не меняя
профили или реакции в БД. Выдача читает профили из БД в порядке position.

## Инварианты и транзакции

Активный мэтч существует тогда и только тогда, когда сохранены оба Like
и нет блокировки ни в одну сторону. Активность управляется командами пары;
FK/UNIQUE/CHECK дополняют этот протокол, но не проверяют связь флагов между
двумя таблицами. Прямое изменение этих таблиц вне команд не является API.

Все три писателя пары — `Like`, `Block`, `Unlike` — выполняют одинаковый порядок:

1. Проверить ID, построить `domain.NewPairKey(actorID, targetID)`.
2. Открыть `BeginTx` с `pgx.ReadCommitted`, сразу поставить `defer rollback(tx)`.
3. Вызвать `lockPair(ctx, tx, key)`: INSERT ON CONFLICT, затем SELECT FOR UPDATE.
4. После ожидания проверить актуальные флаги и выполнить всю операцию через tx.
5. Вызвать `commit(ctx, tx)` и только после успеха вернуть результат.

Каждая команда работает с одной парой; сначала захватывается `pairs`, затем
читается/изменяется её `matches`. SELECT отсутствующей строки не используется
как защита: `lockPair` создаёт сам ресурс. Ни одна команда пары не изменяет
строку профиля. Удаление профилей и снятие блокировок не входят в этот контракт.

Сеть находится до BeginTx. Чтение блокировки до транзакции не заменяет проверку
под захватом пары. Все SQL внутри команды используют tx, включая вложенные
функции. При технической ошибке результат команды нулевой, причина обёрнута
через `%w`. У всех запросов есть ограниченный context; rollback использует
отдельный context с пределом 2s. Пул допускает 8 соединений.

## Переходы

| Команда | Результат |
| --- | --- |
| Первый Like без запрета | Меняется только флаг автора; matched=false, changed=true, matched_now=false |
| Встречный Like | В одном tx сохраняется флаг и создаётся/активируется единственная запись matches; matched_now=true |
| Повтор Like при прежних условиях | Успешный no-op; changed=false, matched_now=false, повторного UPDATE/INSERT результата нет |
| Like при блокировке в любую сторону | 403 blocked, нет нового бизнес-эффекта; это правило действует и для повтора |
| Block | Устанавливается флаг автора, matches.active становится false; реакции сохраняются; оба изменения в одном tx |
| Повтор Block | changed=false; чужую блокировку команда не снимает |
| Unlike | Сбрасывается только Like автора, matches.active становится false; встречный Like сохраняется; оба изменения в одном tx |
| Повтор Unlike без нового Like | changed=false; блокировка не мешает отозвать собственную реакцию |
| Like после Unlike без блокировки | Новая реакция; при взаимности прежняя запись matches активируется, без второй записи на пару |

Идентичность Unlike — установка текущего собственного Like в false. Если после
отзыва пользователь снова поставил Like, новый DELETE отзывает текущую реакцию.
Это не отмена конкретного исторического запроса. Историю команд не храним.

При Block matched=false и при Unlike matched=false. Changed отражает любое
изменение этой командой, включая прекращение мэтча. Существование и права
проверяются и при повторе. Строка pairs без реакций сама по себе не означает Like.

`PairMatched` читает сохранённый active из matches, ничего не создаёт и не
вызывает Profile API. Как в ЛР3, отсутствие пары/результата, включая неизвестный
targetID, возвращает matched=false. Команды изменения требуют обоих профилей.

Выдача использует `Profiles`, `LikedIDs` и `BlockedIDs` из одного PostgreSQL.
BlockedIDs учитывает оба направления; LikedIDs — только исходящие Like.
Ограничения и фильтр применяются до пагинации. viewed/dislike пока остаются
прежними неизменяемыми учебными ограничениями. Пустой результат — `[]`.
Общий снимок страниц между HTTP-запросами не обещается.

## HTTP

Actor всегда берётся из прежнего middleware `X-Demo-User`, не из JSON.
Прежние ограничения ID, request ID, журналы, таймауты и shutdown сохраняются.

| Метод и путь | Вход | Успех 200 |
| --- | --- | --- |
| `PUT /v1/me/likes/{targetID}` | Пустые query и body | `{"matched":true,"changed":true,"matched_now":true}` |
| `GET /v1/me/pairs/{targetID}` | Пустые query и body | `{"target_id":"u2","matched":true}` |
| `PUT /v1/me/blocks/{targetID}` | Пустые query и body | `{"changed":true,"matched":false}` |
| `DELETE /v1/me/likes/{targetID}` | Пустые query и body | `{"changed":true,"matched":false}` |
| `GET /v1/me/discovery` | Прежние interest, limit, offset; пустой body | Прежние анонимные карточки |
| `GET /v1/profiles/{profileID}` | Пустые query и body; только владелец | `{"id":"u1","name":"u1","bio":"","version":1}` |
| `PUT /v1/profiles/{profileID}` | `{"name":"Марго","bio":"Люблю кино","version":1}`; только владелец | Те же поля профиля с новой version |

Новый GET профиля предназначен только владельцу для редактирования и не
публикует чужие данные. Прежняя логика доступа к полному профилю после мэтча
в демонстрации ЛР1 не расширяется этим маршрутом.

Для PUT профиля: body <= 4096 байт, ровно один JSON-объект, только name/bio/version;
все три поля обязательны, bio может быть пустым, version — целое > 0.
Name обрезается по краям; bio сохраняется как передано. Query запрещён.
DTO HTTP отделён от `domain.ProfileEdit`: входная version передаётся как
ExpectedVersion. Успешный повтор со старой версией получает version_conflict.

Полина в коротком tx читает профиль FOR UPDATE: отсутствие → 404, затем чужой
actor → 403, затем сравнение версии и UPDATE ... WHERE version = expected
RETURNING version. Даже сохранение тех же значений увеличивает версию.
После конфликта клиент перечитывает профиль и согласует правку.

## Ошибки

Формат прежний: `{"code":"blocked","message":"Like is blocked"}`.
Внутренняя причина остаётся в логах. Прежние коды ЛР3 сохраняются.

| Причина | HTTP | code / ошибка Go |
| --- | --- | --- |
| Плохой заголовок, ID, query, body | 400 | Прежние invalid_demo_user / invalid_id / invalid_query / invalid_body |
| Like самому себе | 409 | self_like, прежний LikeDeniedError |
| Block/Unlike/чтение пары с собой | 400 | invalid_id / domain.ErrInvalidPair |
| Неактивный профиль для Like | 409 | inactive_profile, прежний LikeDeniedError |
| Нет профиля для команды или редактора | 404 | profile_not_found / domain.ErrProfileNotFound |
| Чужой профиль в редакторе | 403 | forbidden / domain.ErrForbidden |
| Блокировка пары для Like | 403 | blocked / domain.ErrBlocked |
| Старая версия | 409 | version_conflict / domain.ErrVersionConflict |
| Отказ/таймаут Profile API | 502 / 504 | dependency_unavailable / dependency_timeout |
| Бюджет ожидания БД истёк | 504 | database_timeout / context.DeadlineExceeded |
| Deadlock или serialization failure | 503 | transaction_retryable / domain.ErrTransactionRetryable |
| Нет подтверждения Commit | 503 | commit_unconfirmed / domain.ErrCommitUnconfirmed |
| Остальная техническая ошибка | 500 | internal_error |

classify распознаёт SQLSTATE 40001/40P01 и только FK профилей пары как отсутствие
профиля. Остальные нарушения схемы не маскируются под предметный отказ.
Версия проверяется явно: ноль строк UPDATE сам по себе не означает 404.

Автоматического retry нет. При commit_unconfirmed клиент читает результат
пары/профиля, чтобы установить исход. Like/Block можно повторить с их текущей
семантикой; запоздавший Unlike отзывает текущую реакцию, поэтому его нельзя
слепо отправлять после нового Like. Для профиля нельзя автоматически заменить
version в старом payload. Сам timeout/обрыв ответа не доказывает откат.

## Проверки и интеграция

Тесты PostgreSQL используют build tag `dbintegration`, отдельную schema на тест,
настоящие транзакции и разные соединения. Без TEST_DATABASE_URL они завершаются
ошибкой. Обычные тесты ЛР1–ЛР3 запускаются прежней командой `go test ./...`.

Конкуренцию проверяем в обоих значимых порядках: встречные Like и повторы;
Like/Block; встречный Like/Unlike. Проверяются ответы, флаги, active и число
записей matches. Барьер подтверждает захват/ожидание ресурса БД, а не только
запуск goroutine. После отмены ожидания следующая команда должна пройти.
Промежуточный SQL-отказ откатывается; состояние проверяется другим соединением.

После PR операций Марго подключает общий Store вместо memory к серверу и
выдаче, добавляет новые маршруты и DATABASE_URL, закрывает pool при остановке.
Проверяем прежний HTTP-сценарий, отказы Profile API, сохранность результата
после перезапуска и работу двух экземпляров на одной БД. Пока эти части не
подключены, запуск cmd/server не является демонстрацией PostgreSQL.

Каждая работа идёт отдельным PR в develop. Review: Полина → Арина,
Даша → Полина, Марго → Даша, Арина → Марго. Общие сигнатуры и миграцию меняем
согласованно; после применения 001 новые изменения оформляем файлом 002.

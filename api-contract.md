# HTTP-контракт ЛР3

Это контракт общей сборки команды в `cmd/server`. Команды запуска приложения,
локального Profile API и сценария запросов находятся в README.
Старые демонстрации ЛР1–ЛР2 продолжают работать.

## Пользователь и вход

Все бизнес-маршруты получают текущего пользователя из `X-Demo-User`.
Middleware один раз проверяет заголовок и сохраняет ID в context.
Это учебная идентичность: любой клиент может подставить заголовок.
Предметные ограничения проверяет application-слой.

Формат ID: от 1 до 64 байт, без `/`, управляющих символов и пробельных символов
по краям. Один формат применяется к `X-Demo-User` и `targetID`.
Отсутствующий, пустой или повторённый заголовок пользователя даёт `400`.

Все три бизнес-маршрута принимают только пустое тело. Непустое тело отклоняется
до вызова use case с `400 invalid_body`; для проверки достаточно прочитать один
байт. `actor`, `role` и вычисленные поля нельзя передать через JSON или query.
Успешные ответы и обработанные ошибки имеют `Content-Type: application/json`.
Неизвестный маршрут или метод может получить стандартный ответ ServeMux `404/405`.

## Маршруты

### PUT /v1/me/likes/{targetID}

Query-параметров и тела нет. Успех — `200`:

```json
{"matched":false,"changed":true,"matched_now":false}
```

Проверка допуска выполняется до изменения памяти и использует Profile API.
Затем `matching.DecideLike` вычисляет переход внутри атомарного `Update`.
Первый Like меняет только флаг его автора. Ответный Like создаёт взаимность:
`matched=true`, `changed=true`, `matched_now=true`.

Повтор команды при прежних условиях успешен: `changed=false`, новой записи нет.
После взаимности повтор возвращает `matched=true`, `matched_now=false`.
Проверка допуска выполняется и для повтора, поэтому изменение условий может
привести к предметному отказу.

### GET /v1/me/pairs/{targetID}

Query-параметров и тела нет. `targetID` должен отличаться от текущего пользователя.
Успех — `200`:

```json
{"target_id":"u2","matched":false}
```

Чтение использует тот же store, ничего не сохраняет и не обращается к Profile API.
Если пары нет, возвращается `matched=false`, в том числе для неизвестного профиля.

### GET /v1/me/discovery

Допустимы только однократные `interest`, `limit`, `offset`:

| Параметр | Значение |
| --- | --- |
| `interest` | Необязательный общий интерес: фильм, музыка или книга. Пробелы по краям убираются, регистр сохраняется, сравнение точное. Без параметра действует прежний подбор, пустое значение даёт `400`. |
| `limit` | По умолчанию `20`, целое число от `1` до `50`. |
| `offset` | По умолчанию `0`, целое неотрицательное число. |

Неизвестные, повторённые и некорректные параметры дают `400` до бизнес-вызова.
Сначала применяются прежние ограничения и фильтр, затем пагинация. Сохраняется
порядок исходных профилей. Уже лайкнутые текущим пользователем кандидаты
исключаются по актуальным данным общего store.

Успех — `200`, пример карточки:

```json
{"items":[{"candidate_id":"u2","common_movies":["Dune"],"common_music":[],"common_books":[]}],"limit":2,"offset":0}
```

Имя, фото и полный профиль не публикуются. Пустая страница, в том числе offset
за концом списка, возвращает `{"items":[],"limit":2,"offset":100}`.
Между запросами список может измениться; общий снимок нескольких страниц не обещается.

## Ошибки

Общая форма: `{"code":"blocked","message":"Like is blocked"}`.
`message` объясняет причину, а `code` остаётся стабильным.
Внутренний `err.Error()` не возвращается клиенту.

| Причина | Статус | code |
| --- | --- | --- |
| Нет корректного `X-Demo-User` | 400 | `invalid_demo_user` |
| Неверный `targetID`, чтение пары с самим собой | 400 | `invalid_id` |
| Неверный или запрещённый query | 400 | `invalid_query` |
| Непустое тело | 400 | `invalid_body` |
| Like самому себе | 409 | `self_like` |
| Неактивный профиль | 409 | `inactive_profile` |
| Блокировка в любую сторону | 403 | `blocked` |
| Нет обязательного профиля | 404 | `profile_not_found` |
| Ошибка сети, upstream 500, неверный или слишком большой ответ | 502 | `dependency_unavailable` |
| Истёк бюджет ожидания зависимости | 504 | `dependency_timeout` |
| Неожиданная внутренняя ошибка | 500 | `internal_error` |

Обёрнутые причины распознаются через `errors.Is`/`errors.As`.
После отмены клиентского соединения JSON-ответ не гарантируется; отменяемая
работа должна прекратиться. Ошибка зависимости до перехода не создаёт запись.
Отмена после уже выполненной записи не обещает откат.

## Конфигурация и ресурсы

Настройки читает `webserver.LoadConfig` из environment. Длительности задаются
в формате Go, например `700ms` или `3s`; длительности и лимит body положительны.
Некорректное значение возвращает ошибку с именем настройки.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `HTTP_ADDR` | `127.0.0.1:8080` | Адрес приложения |
| `PROFILE_URL` | `http://127.0.0.1:8081` | Локальная HTTP-зависимость |
| `COMMAND_TIMEOUT` | `700ms` | Общий бюджет бизнес-запроса и значение ReadTimeout |
| `CLIENT_TIMEOUT` | `600ms` | Предел одного HTTP-вызова зависимости |
| `DIAL_TIMEOUT` | `200ms` | Установка соединения |
| `RESPONSE_HEADER_TIMEOUT` | `400ms` | Ожидание заголовков зависимости |
| `TLS_HANDSHAKE_TIMEOUT` | `300ms` | TLS-handshake для HTTPS |
| `PROFILE_MAX_BYTES` | `4096` | Максимальный ответ Profile API |
| `READ_HEADER_TIMEOUT` | `2s` | Чтение заголовков входящего запроса |
| `IDLE_TIMEOUT` | `30s` | Простой входящего keep-alive соединения |
| `SHUTDOWN_TIMEOUT` | `3s` | Время ожидания активных запросов при остановке |

Один `http.Client` создаётся при сборке и переиспользуется. Последовательные
запросы профилей получают один context команды и делят оставшийся бюджет.
Profile-клиент читает максимум `PROFILE_MAX_BYTES+1`, обнаруживает превышение
и закрывает response body. Настройка лимита передаётся в его конструктор.

Сервер ограничивает заголовки 16 KiB и задаёт таймауты чтения заголовков и простоя.
`ReadTimeout` берётся из `COMMAND_TIMEOUT` и ограничивает чтение запроса, включая
тело. Срок отсчитывается от начала чтения запроса; заголовки дополнительно имеют
свой `ReadHeaderTimeout`. Так клиент, отправивший заголовки и задержавший тело,
не оставляет обработчик ждать первый байт неограниченно. Ошибка чтения запрещённого
тела приводит к `400 invalid_body` до вызова use case.
Context ограничивает работу обработчика и обращения к зависимости.
`WriteTimeout` не устанавливается, чтобы обработчик мог отправить `504`
при штатном timeout зависимости.

Сервер создаёт новый `X-Request-ID` для каждого запроса, игнорируя входное значение.
Короткая запись slog содержит этот ID, метод, путь, статус и длительность.
Внутренние ошибки связываются с запросом через тот же ID. Тела запросов не логируются.

`Run` при отмене контекста остановки вызывает `Shutdown` с отдельным ограниченным
контекстом. Если grace истёк, вызывается `Close` и возвращается ошибка.
`http.ErrServerClosed` при штатной остановке считается ожидаемым результатом.
В `cmd/server` сигналы `SIGINT` и `SIGTERM` отменяют контекст остановки через
`signal.NotifyContext`, после чего `Run` выполняет этот порядок завершения.

## Общее хранилище

Согласованные сигнатуры `memory.PairStore`:

```go
Load(key domain.PairKey) (domain.PairState, bool, error)
Save(key domain.PairKey, state domain.PairState) error
Update(key domain.PairKey,
    change func(domain.PairState) (domain.LikeDecision, error),
) (domain.LikeDecision, error)
LikedIDs(actorID domain.UserID) ([]domain.UserID, error)
```

`Load`, `Save`, `Update` и `LikedIDs` используют один mutex store.
В `Update` чтение, чистое правило и сохранение выполняются под одной блокировкой.
Сеть и проверки допуска выполняются до `Update`. Callback не должен вызывать
методы этого store. Ошибка callback возвращает нулевой результат без записи.
При `Changed=false` записи нет; результат возвращается после завершения операции.

`LikedIDs` учитывает направление Like, возвращает отдельный отсортированный slice
и пустой `[]`, если лайков нет. Счётчик `Writes()` нужен для проверки эффектов.
Старые `Load`/`Save` сохранены для ЛР2, но их последовательность не является
атомарной командой; HTTP-путь должен использовать `Update`.

Память общая только внутри одного процесса. После перезапуска данные теряются.
Разные экземпляры приложения не делят ни память, ни блокировку.

## Ответственность и проверки

| Часть | Прежняя логика и новая часть | Автор |
| --- | --- | --- |
| PUT Like, GET пары | `application.Service`, `matching.DecideLike`, HTTP-обработчики | Арина |
| Допуск и Profile API | `likes.Service`, HTTP-клиент и локальная зависимость | Полина |
| GET выдачи | Прежние `available`/`interests`, фильтр и пагинация, актуальные Like | Даша |
| Общая память и сборка | Атомарный store, настройки, middleware, остановка, CI | Марго |

Проверки хранилища, HTTP-обвязки и общей сборки:

```sh
go test -count=1 ./internal/memory ./internal/webserver
go test -count=1 ./cmd/server -run TestHTTP -v
go test -race -count=1 ./...
```

Тест хранилища запускает одновременные повторы и встречные Like: итог содержит
обе реакции, ровно два изменения и записи, `MatchedNow` возникает один раз.
Тест остановки использует каналы: ждёт начала обработки, запускает Shutdown,
проверяет ожидание завершения и принудительное закрытие при истечении grace.
Отдельный сетевой тест отправляет заголовки chunked-запроса без тела и проверяет,
что чтение первого байта завершается по таймауту и сервер может отправить отказ.
`TestHTTPScenario` в `cmd/server` проверяет две страницы выдачи, первый Like,
повтор без записи, встречный Like и чтение сохранённого результата с обеих сторон.
Отдельные HTTP-тесты проверяют отказы зависимости без сохранения пары,
восстановление после ошибки и цепочку отмены от клиента до Profile API.
`TestConcurrentLikesAcrossServices` в `internal/integration` проверяет две
application-службы на одном store: две записи и один `MatchedNow`.
